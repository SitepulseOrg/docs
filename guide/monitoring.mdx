The **Monitoring** page in the sidebar controls how SitePulse runs automatic checks and when monitoring problems open issues for your team. Admins and owners can edit these settings; members can view them.

<Info>
  Individual [sites](/guide/sites) can override cadence, thresholds, and other issue settings. Team defaults apply when a site has no override.
</Info>

## Two save sections

The Monitoring page has two independent forms:

| Section | What it controls | Save button |
|---------|------------------|-------------|
| **Monitoring settings** | Per-tool automatic check cadence and team status-check header | Save monitoring settings |
| **Issue settings** | Enabled issue tools, quiet time, escalation, and problem thresholds | Save issue settings |

Changes to one section do not affect the other until you save that section.

## Automatic check cadence

For each enabled check tool, choose how often SitePulse runs **automatic** checks:

- Status
- SSL
- DNS
- Broken Links
- Performance

Cadence presets range from every minute to every week. Your [plan](/guide/team-management#plans) sets the **fastest** cadence allowed (Starter: 30 minutes, Growth: 5 minutes, Agency: 1 minute). Presets faster than your plan minimum are disabled in the dropdown.

When you change a site's enabled checks or cadence overrides, SitePulse resyncs that site's automatic schedules.

## Status check header

Set a default HTTP header for **status** checks across the team. Use this when monitored sites require authentication or a custom header to respond correctly.

Format: header **name** and **value** (for example `Authorization` and a bearer token).

Sites can override this header on the [site edit page](/guide/sites#editing-a-site).

## Quiet time

Quiet time suppresses **outbound** notifications (email, Slack, Teams, webhooks, in-app alerts) during a daily window.

| Setting | Description |
|---------|-------------|
| **Enabled** | Turn quiet time on or off |
| **From** | Start time (team timezone) |
| **Until** | End time (team timezone) |

Checks continue to run during quiet time. Issues can still open, acknowledge, and resolve — only alerts are suppressed.

See [Notifications](/guide/notifications#quiet-time) for how quiet time interacts with each channel.

## Issue settings

Issue settings define when automatic monitoring **opens** or **resolves** issues and sends notifications. Configure defaults here; override per site when needed.

Each check tool has its own **collapsible** section on the Monitoring page. Use the section headers to expand or collapse Status, SSL, Performance, Broken Links, and DNS rules. The page sidebar includes an **Escalation** anchor that jumps to follow-up notification settings.

### Enabled issue tools

Each check tool has an **Enabled** / **Disabled** toggle. When disabled, automatic checks for that tool still run and save results, but they do not open or resolve issues.

Use this to monitor a tool without generating incidents (for example, run performance checks for trends only).

### Default thresholds

New teams inherit these defaults (from SitePulse configuration):

| Tool | Setting | Default |
|------|---------|---------|
| **Status** | Failures to open incident | 2 |
| **Status** | Resolve after successes | 1 |
| **Status** | Confirmation retry (minutes) | 2 |
| **Status** | Follow-up while open (minutes) | 5 |
| **SSL** | Expiry window (days) | 14 |
| **Broken links** | Minimum broken links | 5 |
| **Broken links** | Failures to open incident | 1 |
| **Broken links** | Ignore external links | Off |
| **Broken links** | Ignore redirects | Off |
| **Performance** | Minimum score | 50 |
| **Performance** | Max TTFB (ms) | 4000 |
| **Performance** | Max load time (seconds) | Not set |
| **Performance** | Failures to open incident | 2 |
| **DNS** | Hard failures only | On |
| **DNS** | Monitored record types | A, AAAA, CNAME, MX, NS, TXT |
| **Escalation** | Enabled | Off |

For full threshold behavior, see [Problem thresholds](/guide/checks#problem-thresholds).

### Status failure threshold

For status checks, choose how many consecutive failures are required before SitePulse opens an issue:

| Preset | Failures to open |
|--------|------------------|
| **Instant** | 1 |
| **Conservative** | 3 |
| **Aggressive** | 1 |
| **Custom** | Any value you enter |

The preset sets **Failures to open**. Other status fields (successes to resolve, confirmation retry, incident follow-up) stay independent.

### Performance thresholds

Performance issue rules use three separate breach checks:

| Setting | Description |
|---------|-------------|
| **Minimum score** | Lowest acceptable Lighthouse performance score (1–100) |
| **Max TTFB (ms)** | Slowest acceptable time to first byte in milliseconds |
| **Max load time (seconds)** | Slowest acceptable Time to Interactive (TTI), measured in seconds |

A performance check breaches when **any** configured limit is exceeded. Leave **Max load time** empty to skip load-time evaluation.

### DNS expected records

For DNS issue detection, enter expected records **one per line**:

```
A 203.0.113.1
CNAME example.hosting.com
TXT v=spf1 include:_spf.example.com ~all
```

Supported types: `A`, `AAAA`, `CNAME`, `MX`, `NS`, `TXT`.

Select which record types to **monitor for changes** with the checkboxes under DNS issue rules. Only selected types are compared against expected records and stored on the first DNS check.

SitePulse opens a DNS issue when:

- A DNS lookup **hard fails**, or
- **Hard failures only** is off and a monitored expected record is missing or changed

When **Hard failures only** is on, SitePulse ignores expected-record mismatches and opens issues only for lookup failures.

### Broken links and crawlers

If broken-link checks return many `503` responses, the target site may be blocking crawlers. Add `SitepulseBot` to the site's `robots.txt` allowlist.

Team-level broken-link filters on this page:

| Setting | Description |
|---------|-------------|
| **Ignore external links** | Exclude links whose host differs from the monitored site |
| **Ignore redirects** | Exclude links that return `301`, `302`, or `303` |
| **Ignore paths** | URL path patterns excluded from the crawl (one per line; supports wildcards such as `/wp-admin/*`) |

Sites can still override **ignore paths** on the [site edit page](/guide/sites#site-specific-overrides).

### Escalation

Escalation sends **follow-up reminders** while an issue stays open or acknowledged. Reminders use the same destinations as **Issue detected** notifications (email, Slack, Teams, webhooks, in-app).

| Setting | Description |
|---------|-------------|
| **Enabled** | Turn escalation on or off for the team |
| **Intervals** | When to re-notify after an issue opens: 15 minutes, 30 minutes, 1 hour, 6 hours, or daily |

Escalation does not open new issues. It re-sends alerts on the schedule you choose until the issue is resolved or no longer active. Quiet time suppresses escalation reminders the same way it suppresses other outbound alerts.

See [Notifications](/guide/notifications#issue-escalation) for how escalation interacts with notification configurations.
